# Takeaway

The POC's rendering and body pipeline are reusable, but its **garment is code, not data**. Every
neckline, back, leg line and accent is an analytic function written in reference-body metres
inside `regions()` in `poc-threejs/src/body.js`.[^body-js] A designer cannot change a shape, a
seamstress cannot get a flat piece, and nothing can be saved. The central engineering task of the
next phase is a **garment data model**: panels bounded by editable curves on the body, each with
a fabric stack, that both renders in 3D and flattens to pattern pieces.

# What the POC does today

| Area | POC implementation | Reusable? |
|---|---|---|
| Bodies | Four MakeHuman mannequins with identical topology; designs carried between sizes by vertex index (see [mannequin pipeline](/engineering/pipeline/mannequin-pipeline.md)) | Yes: the shared-topology idea is the basis for size transfer |
| Garment shape | `regions(v, style)` returns signed-distance-like fields per vertex: neck (scoop, keyhole, strappy back), leg line, sleeve, one Bezier "swoosh" accent; thresholded per pixel[^body-js] | **No**: fixed shapes, three fixed zones (body, sleeve, accent) |
| Fabric bridging hollows | `computeLift`: outward-only membrane diffusion, capped at 3 cm | Yes |
| Fabrics | `MeshPhysicalMaterial` plus injected procedural layers (see [fabric shader](/engineering/poc/fabric-shader.md)) | Yes, as the material system |
| Stones | Instanced crystals and spangles with an inner-reflection shader; patterns generated by code (see [stones](/engineering/poc/stones.md)) | Renderer yes; placement must become editable strokes |
| State | One in-memory `state` object driven by lil-gui; "looks" are presets[^main-js] | No: no document, no save, no undo |
| Output | Screen only | No pattern, DXF, stone map or spec output |

# What the professional tool needs

Derived from the owner's role descriptions:[^owner]

1. **A design document**, serialisable and versioned, that every role opens.
2. **Panels and seams as data.** **[INFERRED]** A seam graph of curves drawn on the reference body
   surface; closed regions between curves are panels; each panel has a fabric stack (outer,
   optional lining) and a construction method per boundary (pieced seam, appliqué, print,
   finished edge such as elastic or binding).[^report]
3. **Openings and straps.** Cut-outs are panels with no fabric and a finished edge; straps are
   paths with width that may leave the skin and bridge (the lift solve covers the hollows).
4. **Flattening.** Each panel flattened to a 2D piece with seam allowance, notches, grain/stretch
   direction and labels; stones mapped per piece in the relaxed state. See
   [/engineering/geometry/](/engineering/geometry/about.md).
5. **Size transfer.** Curves and stones stored as surface addresses on the shared-topology body,
   so one design evaluates on every size; per-size counts reported.
6. **Editable strokes and undo** for stones and curves.
7. **Role-gated views** over the same document (see [role capabilities](/product/role-capabilities.md)),
   including template locks so designers decide what coaches may change.

# Risks

- **[INFERRED]** Curves on the body must stay valid when edited near seams, arms and the crotch,
  where the POC's analytic fields relied on hand-tuned constants.
- Flattening is a solved calculation, but turning a flattened panel into a cuttable piece depends
  on negative ease, which is per-fabric factory knowledge with no standard.[^report]
- The renderer currently draws each zone as a full-body pass with per-pixel discard; many panels
  would multiply draw cost unless panels are packed into one pass (for example a panel-ID
  texture). **[INFERRED]**
