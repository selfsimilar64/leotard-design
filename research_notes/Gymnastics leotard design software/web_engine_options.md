## 1. What exactly do the current releases of three.js, Babylon.js and PlayCanvas support for each requirement, what is missing, and how do experienced developers compare them in 2025-2026?

### Takeaway
All three are actively released (three.js r186, September 2026; Babylon.js 9.30.0, 8 October 2026; PlayCanvas 2.23.2, 9 October 2026), permissively licensed, and cover the glTF-level advanced material set (sheen, clearcoat, anisotropy, thin-film iridescence, transmission), HDRI lighting, area lights and a post-processing stack; none ships a procedural glint/glitter or diffraction BRDF, so that part is custom shader work in every option. They differ mainly in how custom shading is authored (three.js: TSL node system with a subclassable lighting model; Babylon.js: material plugins, Node Material and an OpenPBR material; PlayCanvas: shader-chunk overrides that must be written in both GLSL and WGSL), in how their own maintainers label WebGPU maturity (three.js: experimental; Babylon.js: complete; PlayCanvas: beta), and in how many editor primitives ship in the core.

**Requirement 1 — advanced materials, transparency, custom shader authoring**
- three.js `MeshPhysicalMaterial` documents anisotropy (strength, direction map, rotation), clearcoat (with separate roughness and normal map), iridescence (IOR and thickness range), sheen (colour, roughness, maps), transmission with thickness/attenuation/dispersion, specular colour/intensity, and a `retroreflectivity` parameter. — [MeshPhysicalMaterial docs](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)
- Recent three.js material work: r183 added clearcoat support for rect area lights; r186 added retroreflectivity and adjusted multi-scattering and diffuse/sheen energy conservation; r181 changed indirect specular so rough materials get brighter. — [GitHub releases](https://github.com/mrdoob/three.js/releases); [Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- three.js WebGPU examples exist for sheen, anisotropy, iridescence, clearcoat, transmission, dispersion and retroreflection. — [three.js examples index](https://threejs.org/examples/files.json)
- In three.js's WebGPURenderer, `ShaderMaterial`, `RawShaderMaterial` and `onBeforeCompile` are not supported; custom materials must be written as node materials in TSL. — [three.js WebGPURenderer manual](https://threejs.org/manual/pages/webgpurenderer.html)
- TSL node materials expose slots such as `colorNode`, `positionNode`, `normalNode`, `roughnessNode`, `fragmentNode`/`vertexNode` and a `lightsNode` slot that defines the lights and lighting model used by the material. — [Three.js Shading Language wiki](https://github.com/mrdoob/three.js/wiki/Three.js-Shading-Language)
- three.js r186 has an abstract `LightingModel` class with overridable hooks `start`, `finish`, `direct`, `directRectArea`, `indirect` and `ambientOcclusion`; the official `webgpu_lights_custom` example subclasses it and attaches it through a `lightsNode` context. — [LightingModel.js (r186)](https://github.com/mrdoob/three.js/blob/r186/src/nodes/core/LightingModel.js); [webgpu_lights_custom (r186)](https://github.com/mrdoob/three.js/blob/r186/examples/webgpu_lights_custom.html)
- three.js r186 ships an official order-independent-transparency example that uses weighted-blended OIT through an `OITPassNode` add-on, plus an alpha-hash example. — [webgpu_oit (r186)](https://github.com/mrdoob/three.js/blob/r186/examples/webgpu_oit.html); [three.js examples index](https://threejs.org/examples/files.json)
- Babylon.js core 9.30.0 contains dedicated PBR configuration modules for sheen, clearcoat, anisotropy, iridescence and subsurface. — [@babylonjs/core 9.30.0 PBR files](https://app.unpkg.com/@babylonjs/core@9.30.0/files/Materials/PBR)
- Babylon.js `OpenPBRMaterial` was announced as alpha in the 9.0 series (2 April 2026) and credited as a contribution from Adobe; the announcement says many OpenPBR parameter groups (base, specular, coat, thin-film and others) map to the existing PBR system. — [Babylon.js 9.0 Part 3](https://blogs.windows.com/windowsdeveloper/2026/04/02/part-3-babylon-js-9-0-openpbr-and-additional-engine-updates/)
- Verified in package: in 9.30.0 the `OpenPBRMaterial` class exposes base (including diffuse roughness), specular (including roughness anisotropy), coat (including darkening and coat anisotropy), fuzz (colour, roughness, weight), thin-film (weight, thickness, IOR), transmission (including dispersion and scatter), subsurface, emission and geometry (tangent, coat tangent, thin-walled, opacity) parameters. — [openpbrMaterial.pure.d.ts 9.30.0](https://app.unpkg.com/@babylonjs/core@9.30.0/files/Materials/PBR/openpbrMaterial.pure.d.ts)
- The Babylon.js OpenPBR documentation page still lists the fuzz, transmission, subsurface, emission and geometry parameter groups as awaiting evaluation, i.e. the docs lag the shipped class. — [Babylon.js OpenPBR docs](https://doc.babylonjs.com/features/featuresDeepDive/materials/using/OpenPBR/)
- A Babylon.js forum maintainer advised relying on `PBRMaterial` until `OpenPBRMaterial` stabilises because of possible breaking changes (thread date not captured). — [Babylon.js forum](https://forum.babylonjs.com/t/does-openpbrmaterial-now-support-rendering-light-shadows-now/60904)
- Babylon.js material plugins inject custom shader code into Standard/PBR materials at named insertion points or by regular-expression replacement, should be supplied in both GLSL and WGSL, and the documentation warns that insertion-point names, patterns and variable names are not guaranteed stable across versions. — [Babylon.js material plugins docs](https://doc.babylonjs.com/features/featuresDeepDive/materials/using/materialPlugins)
- Babylon.js's Node Material Editor has been able to produce WGSL shaders since 8.0. — [Babylon.js 8.0 announcement](https://blogs.windows.com/windowsdeveloper/2025/03/27/announcing-babylon-js-8-0/)
- Babylon.js transparency: alpha-blended meshes are sorted per mesh by distance (bounding-sphere centre), with depth pre-pass, separate culling pass and facet depth sort as mitigations; an OIT mode (`scene.useOrderIndependentTransparency`) uses dual depth peeling with a default of 5 passes (about 10 layers), is described as beta, does not work with anti-aliasing, does not support refraction textures, and requires WebGL 2 or WebGPU. — [Babylon.js transparent rendering docs](https://doc.babylonjs.com/features/featuresDeepDive/materials/advanced/transparent_rendering)
- PlayCanvas `StandardMaterial` (API reference v2.23.1) exposes sheen (`useSheen`, sheen colour and gloss maps), clearcoat (intensity, gloss, normal map), anisotropy (requires GGX specular; intensity, rotation, map), thin-film iridescence (intensity, thickness min/max, refraction index), refraction with attenuation and optional grab-pass dynamic refraction, and dispersion. — [PlayCanvas StandardMaterial API](https://api.playcanvas.com/engine/classes/StandardMaterial.html)
- PlayCanvas transparency options in the same API: blend types, `opacityDither` (dithered transparency without blending) and `alphaToCoverage` (needs a multisampled target); no class or constant for order-independent transparency appears in the 2.23.2 export list. — [PlayCanvas StandardMaterial API](https://api.playcanvas.com/engine/classes/StandardMaterial.html); [playcanvas.d.ts 2.23.2](https://app.unpkg.com/playcanvas@2.23.2/files/build/playcanvas.d.ts)
- PlayCanvas customisation: individual shader chunks can be replaced (`Material#getShaderChunks`), an `onUpdateShader` hook runs before shader generation, and `ShaderMaterial` takes fully custom vertex/fragment source in GLSL (WebGL) and/or WGSL (WebGPU) — both are needed to run on both backends. — [PlayCanvas StandardMaterial API](https://api.playcanvas.com/engine/classes/StandardMaterial.html); [playcanvas.d.ts 2.23.2](https://app.unpkg.com/playcanvas@2.23.2/files/build/playcanvas.d.ts)
- PlayCanvas splits its lit shader into a material front end (surface properties) and a lighting back end (lights, shadows, reflections); the docs say that since v1.62 the back-end inputs are fixed so a fully custom shader can call the engine's lighting code, but the `LitMaterial` class that embodies this split is marked as internal (`@ignore`) in the 2.23.2 typings. — [PlayCanvas shader migrations docs](https://developer.playcanvas.com/user-manual/graphics/shaders/migrations/); [playcanvas.d.ts 2.23.2](https://app.unpkg.com/playcanvas@2.23.2/files/build/playcanvas.d.ts)

- three.js r186 has 17 official `webgpu_compute_*` examples (particles, cloth, bitonic sort, rasteriser, etc.) and an indirect-draw example in which a compute pass writes draw arguments into an `IndirectStorageBufferAttribute` bound with `geometry.setIndirect()`. — [three.js examples index](https://threejs.org/examples/files.json); [webgpu_struct_drawindirect (r186)](https://github.com/mrdoob/three.js/blob/r186/examples/webgpu_struct_drawindirect.html)

- PlayCanvas indirect drawing is WebGPU-only: draw parameters live in a GPU storage buffer that a compute shader can write (GPU culling, dynamic instance counts); slots must be re-allocated each frame, the default cap is 1,024 indirect draws per frame, and on other platforms the mesh instance renders as a normal draw. — [PlayCanvas indirect drawing docs](https://developer.playcanvas.com/user-manual/graphics/advanced-rendering/indirect-drawing/)
- PlayCanvas `Compute` and `StorageBuffer` are documented in the typings as WebGPU-only; 2.23.0 moved mesh-instance matrices into a persistent storage buffer and added partial vertex/index buffer uploads on WebGPU; the engine ships a `ComputeRadixSort`. — [playcanvas.d.ts 2.23.2](https://app.unpkg.com/playcanvas@2.23.2/files/build/playcanvas.d.ts); [PlayCanvas engine releases](https://github.com/playcanvas/engine/releases)

**How developers compare them (2025–2026)**
- A three.js forum reply (6 February 2026, community member; a single opinion, not a maintainer statement) to a question about whether a new project should use WebGPURenderer recommends the WebGL renderer for stability and broad compatibility, describes WebGPU support in three.js and R3F as still catching up, and says post-processing and materials are not at full parity. — [three.js forum](https://discourse.threejs.org/t/webgpu-renderer-vanilla-three-js-vs-r3f-maturity-and-pitfalls/89661)
- A comparison by the CTO of Cinevva (a vendor of a competing WebGPU-only platform; June 2026, versions updated September 2026) characterises three.js as a rendering library rather than an engine with the largest web-3D community and no bundled editor/physics/entity system; Babylon.js as the all-in-one option (bundled physics and a free web editor) with WebGPU work among the more advanced of the general-purpose engines; and PlayCanvas as WebGL2-first with a still-maturing WebGPU path, strong Gaussian-splat tooling and a commercial hosted editor. — [Cinevva comparison](https://app.cinevva.com/blog/2026-06-09-web-game-engines-2026-comparison)
- Maxime Heckel (14 October 2025) reports that TSL's node system is its selling point but that its functional syntax costs legibility, that he hit many gotchas and undocumented features (for example sampler handling), that TSL post-processing was less documented than expected, and that R3F's `extend` needed workarounds. — [Field Guide to TSL and WebGPU](https://blog.maximeheckel.com/posts/field-guide-to-tsl-and-webgpu/)
- Steven Wittens (January 2023, older) considers three.js good for classic 3D but finds application-building on R3F fragile because of how change handling is defined. — [Use.GPU Goes Trad](https://acko.net/blog/use-gpu-goes-trad/)

### Inferences
- None of the three has a built-in glint/glitter or diffraction BRDF; the decisive difference for requirement 1 is the extension mechanism. three.js's `LightingModel` hook is the most direct documented way to replace or extend the per-light and indirect BRDF while keeping the engine's light loop, shadows and IBL plumbing; Babylon.js's plugin mechanism patches the stock PBR shader by injection and its own docs warn the injection names may change; PlayCanvas requires maintaining paired GLSL and WGSL chunk overrides against a versioned chunk API.
- Sheer fabric: the three engines offer three different trade-offs — three.js weighted-blended OIT (an approximation), Babylon.js depth peeling (exact up to a layer count but beta and incompatible with anti-aliasing), PlayCanvas dither/alpha-to-coverage (relies on MSAA/TAA to hide noise). None is turnkey for layered mesh over skin.
- Sequins: all three can draw 10^4–10^6 instances; GPU-side culling through compute plus indirect draws is WebGPU-only in three.js and PlayCanvas, and was not verified for Babylon.js. Babylon.js thin instances are optimised for static sets, so a paint-to-place workflow needs pre-allocated updatable buffers.
- Babylon.js and PlayCanvas ship more editor primitives in the core (GPU picker, gizmos, outline, inspector) than three.js, which relies on add-ons and the surrounding ecosystem (see section 2).
- Maturity labels differ by maintainer voice as much as by reality: three.js calls its WebGPU renderer experimental while shipping the broadest example set; Babylon.js calls its WebGPU engine complete; PlayCanvas calls WebGPU beta.

## 2. What is the state of three.js's WebGPU renderer and TSL (production readiness, parity gaps, compute, indirect drawing, performance evidence, shipped projects), and what does the surrounding ecosystem add for an editor-style application?

### Takeaway
As of r186 the official manual still describes WebGPURenderer as "still in an experimental state" and says some applications will meet missing features or better performance on WebGLRenderer, yet the feature surface is large (230 official WebGPU examples including compute, indirect draw, OIT, SSGI and HDR output) and at least one professional design tool, Spline v2 (August 2026), ships its runtime on it. Adopting it means writing all custom shading in TSL, accepting breaking changes in nearly every release, and living with an ecosystem that is mid-transition: R3F's WebGPU-first v10 and pmndrs postprocessing v7 are pre-release, while three-mesh-bvh and three-gpu-pathtracer have already moved to WebGPU compute.

### Cited Findings
- Official status: the manual says the renderer is experimental though much matured, that depending on the application there will be missing features or better performance with WebGLRenderer, and that upgrading to the latest release is recommended because it improves each release. — [three.js WebGPURenderer manual](https://threejs.org/manual/pages/webgpurenderer.html)
- WebGLRenderer remains maintained and is the recommended choice for pure WebGL 2 applications, but no larger new features are planned for it; the team is investigating limited node-material support there (r184 added a NodeMaterial compatibility layer). — [three.js WebGPURenderer manual](https://threejs.org/manual/pages/webgpurenderer.html); [GitHub releases](https://github.com/mrdoob/three.js/releases)
- Parity gaps stated officially: no `ShaderMaterial`/`RawShaderMaterial`/`onBeforeCompile`; no `EffectComposer` (replaced by a node-based stack with built-in MRT and automatic pass combination). — [three.js WebGPURenderer manual](https://threejs.org/manual/pages/webgpurenderer.html)
- Initialisation is asynchronous: use `setAnimationLoop()` or `await renderer.init()`; r181 deprecated `renderAsync()`/`computeAsync()` in favour of awaiting `init()`. — [three.js WebGPURenderer manual](https://threejs.org/manual/pages/webgpurenderer.html); [Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- The official example index lists 230 WebGPU examples against 298 WebGL examples; the section key is plain `webgpu`, with no work-in-progress label. — [three.js examples index](https://threejs.org/examples/files.json)
- TSL compute: functions are turned into compute nodes with a count, with `instancedArray`, `storage` and `storageTexture` for buffers/textures, plus atomics and barriers, dispatched with `renderer.compute()`. — [Three.js Shading Language wiki](https://github.com/mrdoob/three.js/wiki/Three.js-Shading-Language)
- WebGL 2 fallback limits: compute is not fully compatible with WebGL 2; indirect draws and atomics are WebGPU-only; the maintainer's advice is to pick a feature set matching the WebGL 2 target and test the compute examples in a WebGL-2-only browser. — [three.js forum (Mugen87, 7 Nov 2025)](https://discourse.threejs.org/t/tsl-and-webgl2-vs-webgpu/87974)
- Release-by-release WebGPU progress in 2026: r183 (PostProcessing renamed RenderPipeline; improved WebGPU shadows; `WebGLCubeRenderTarget` no longer usable with WebGPURenderer), r184 (non-blocking `compileAsync`, async `ReadbackBuffer`, reversed depth with depth32float), r185 (WebXR on WebGPU, rendering to texture arrays, changed premultiplied-alpha handling, uncaptured GPU errors surfaced, `ClusteredLighting` replaces `TiledLighting`), r186 (`compileComputeAsync`, a direct render pipeline, MSAA for WebXR WebGPU). — [GitHub releases](https://github.com/mrdoob/three.js/releases); [Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- Performance evidence: no official benchmark numbers were found; a studio that sells three.js/WebGPU work states that gains depend on the scene, that WebGPU is not faster everywhere, links a forum thread with scenes where WebGPURenderer was slower, and advises profiling before migrating for speed. — [Utsubo](https://www.utsubo.com/blog/threejs-2026-what-changed)
- Shipped on WebGPURenderer (studio-reported): Segments.ai's 3D labelling platform was migrated from WebGL to WebGPU for point clouds with millions of points (qualitative result only); an Expo 2025 Osaka installation ran about one million particles. — [Utsubo](https://www.utsubo.com/blog/threejs-2026-what-changed)
- Shipped on WebGPURenderer (verified in package): the Spline runtime 2.0.79 (published 13 October 2026) ships separate WebGPU and WebGL standalone builds, and the WebGPU build contains three.js identifiers (the multiple-instances warning global, `WebGPURenderer`, `NodeMaterial`, a WGSL node-function error string). — [@splinetool/runtime 2.0.79 files](https://app.unpkg.com/@splinetool/runtime@2.0.79/files/build)
- Spline v2 (announced 20 August 2026) is described as a ground-up rebuild whose renderer is TSL-based WebGPU by default with WebGL fallback, with some features (screen-space reflections) WebGPU-only. — [Create With](https://createwith.com/tool/spline/updates/spline-v2-rebuilds-the-browser-3d-editor-around-ai-agents); [AlternativeTo](https://alternativeto.net/news/2026/8/spline-v2-launches-with-rebuilt-3d-editor-ai-agents-webgpu-and-new-desktop-app/)
- Google's `<model-viewer>` 4.4.0 peer-depends on three ^0.183.0. — [npm registry](https://registry.npmjs.org/@google/model-viewer/latest)
- Reported pitfall: a 2026 migration guide describes a black canvas for a Firefox-on-Linux user after a project shipped on WebGPU, and a black canvas with no console error when the async init is skipped. — [BuildMVPFast](https://www.buildmvpfast.com/blog/threejs-webgl-to-webgpu-renderer-migration-2026)
- react-three-fiber: stable is 9.8.1 (24 September 2026; compatible with React 19.3); v10 is at alpha.5 (8 September 2026) with canary builds published on 13 October 2026. — [R3F releases](https://github.com/pmndrs/react-three-fiber/releases); [npm registry](https://registry.npmjs.org/@react-three/fiber)
- R3F v10 alphas make WebGPU and TSL first-class through a `@react-three/fiber/webgpu` entry point, rename `state.gl` to `state.renderer`, add TSL hooks (`useUniforms`, `useNodes`, `useLocalNodes`) and experimental compute/storage hooks (`useBuffers`, `useGPUStorage`), and replace `usePostProcessing` with `useRenderPipeline`; all are described as experimental with no stable date. — [R3F releases](https://github.com/pmndrs/react-three-fiber/releases)
- With R3F v9, WebGPURenderer works through the asynchronous `gl` prop, with reported friction around `extend`. — [Field Guide to TSL and WebGPU](https://blog.maximeheckel.com/posts/field-guide-to-tsl-and-webgpu/)
- drei: stable 10.7.9, 11.0.0 at alpha.7; described as helpers for R3F; about 4.39M weekly downloads. — [npm registry](https://registry.npmjs.org/@react-three/drei); [pmndrs/drei](https://github.com/pmndrs/drei)
- pmndrs `postprocessing`: stable 6.39.5 (9 September 2026); its README shows `WebGLRenderer` usage only; 7.0.0 is at beta.16; licence Zlib. — [pmndrs/postprocessing](https://github.com/pmndrs/postprocessing); [npm registry](https://registry.npmjs.org/postprocessing)
- three-mesh-bvh 0.9.16 (8 October 2026, MIT, about 4.9M weekly downloads): BVH-accelerated raycasting and spatial queries for three.js meshes; the README claims 500 rays against an 80,000-polygon model at 60 fps; examples include sculpting, triangle painting and lasso selection; BVH generation can run in a web worker, with a parallel worker that needs `SharedArrayBuffer`; supports `BatchedMesh`, skinned-mesh and scene-level BVH variants; limitations include a static BVH (refit or rebuild after geometry edits). — [three-mesh-bvh README 0.9.16](https://cdn.jsdelivr.net/npm/three-mesh-bvh@0.9.16/README.md); [npm downloads API](https://api.npmjs.org/downloads/point/last-week/three-mesh-bvh)

- three-gpu-pathtracer 0.0.27 (8 October 2026, MIT): the README now describes a path tracer built on three-mesh-bvh and WebGPU compute shaders, used via `WebGPUPathTracer` with `THREE.WebGPURenderer`, states that WebGPU is required, supports `MeshStandardMaterial`/`MeshPhysicalMaterial`, area/spot/point lights, environment maps, denoising and upscaling; peer dependency three >= 0.185.0. — [three-gpu-pathtracer README 0.0.27](https://cdn.jsdelivr.net/npm/three-gpu-pathtracer@0.0.27/README.md); [package.json](https://cdn.jsdelivr.net/npm/three-gpu-pathtracer@0.0.27/package.json)

### Inferences
- Production readiness is contested rather than settled: the maintainers' label is experimental, forum advice in February 2026 still leaned to WebGLRenderer, yet a commercial design tool has shipped on it with a WebGL build alongside. A team that pins versions, budgets for per-release migration and keeps a WebGL 2 fallback build is following the pattern that the shipped evidence shows.
- Because TSL compiles to both WGSL and GLSL, a custom fabric/glint BRDF written once can serve both backends; compute-driven features (GPU culling of sequins, indirect draws) need a CPU-side fallback or a reduced mode on WebGL 2.
- An editor on three.js today would assemble picking (three-mesh-bvh), gizmos (add-ons), post-processing (the built-in TSL stack, since the pmndrs library is WebGL-only in stable) and UI glue itself; choosing R3F for a WebGPU-first editor means building on alpha APIs (v10) or integrating manually on v9.
- The WebGPU path tracer in the same scene graph offers a route to a final-quality still render mode alongside the real-time viewport, though the README describes it as a progressive renderer, not a real-time one.

## 4. Filament on the web: material quality (including its cloth model) versus ecosystem and tooling; status of any WebGPU backend

### Takeaway

## 5. Game-engine web exports (Unity, Unreal, Godot): viability and drawbacks

### Takeaway
Unity is the only one of the three with a first-party, in-browser runtime that can use WebGPU: WebGL 2 is the default, and the Unity 6.6 documentation no longer labels WebGPU experimental (6.3 LTS did), though it remains opt-in with a list of limitations. Unreal has no official in-browser target — its supported route is Pixel Streaming, which renders on a server GPU and sends video. Godot 4.7's web export is WebGL 2 only (Compatibility renderer), without C# or WebGPU.

## 6. A hand-rolled WebGPU/WebGL2 renderer: what must be built, reported effort, benefits and risks, and middle paths

### Takeaway
The most demanding web design tools did hand-roll (Figma's C++/WebAssembly renderer; Onshape's custom WebGL renderers), but their public accounts show that the infrastructure beneath any material work — pipeline and bind-group caching, uniform batching, shader cross-compilation, asynchronous readback, device-loss handling and a WebGL fallback — is itself a multi-phase engineering project. No source found gives a person-month figure for a PBR-grade WebGPU renderer. Middle paths are well populated: thin typed layers over WebGPU, Rust or C++ compiled to WebAssembly, or keeping an engine and replacing only its lighting model and material nodes.

### Cited Findings
- A WebGPU case study on efficiently rendering glTF (last updated 29 February 2024) walks from a naive renderer through buffer-binding normalisation, pipeline de-duplication and caching, re-ordering the render loop (pipeline → primitive → instance), instancing via storage buffers with `firstInstance`, and material bind groups with shader variants; it notes that pipeline creation is expensive and causes hitches if done during rendering, that drivers need not remove redundant state changes, and that it leaves transparent-surface sorting unsolved and advanced materials out of scope. — [toji.dev glTF case study](https://toji.dev/webgpu-gltf-case-study/)
- Figma (18 September 2025) moved its C++ renderer (compiled to WebAssembly with Emscripten; native builds use Dawn) from WebGL to WebGPU: it first made draw-call arguments explicit and batched uniform uploads, wrote a custom shader processor that converts its older GLSL to newer GLSL and then to WGSL via naga, handled asynchronous-only readback, and fixed regressions through bind-group caching and better batching. — [Figma: rendering powered by WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)
- Figma found load-time GPU tests insufficient because WebGPU can fail mid-session (device loss), built a dynamic mid-session fallback from WebGPU to WebGL on Windows, and finished rollout by blocklisting devices with high fallback rates; results were improvements on some device classes, neutral on others, no regressions, with no numbers published; planned follow-ups are compute-shader blurs, MSAA and render bundles. — [Figma: rendering powered by WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)
- Figma's 2015 account of why it hand-rolled: HTML/SVG were too slow and 2D canvas is immediate-mode and lacked needed features, so it built a tile-based, fully GPU, anti-aliased WebGL renderer plus its own document model, compositor and text layout, in C++ compiled to asm.js for control over memory layout and to avoid garbage-collection pauses; it hit browser limits in memory allocation, font access, clipboard formats, pinch-zoom input and high-DPI cursors. — [Figma: building a professional design tool on the web](https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/)
- Onshape (28 June 2018) states it uses its own custom WebGL renderers rather than third-party scene-graph libraries, with tessellation computed on geometry servers and triangles sent to the client. — [Onshape: how does Onshape really work](https://www.onshape.com/en/blog/how-does-onshape-really-work)
- Steven Wittens' Use.GPU 0.8 write-up (14 January 2023) describes building scene/instancing/shadow-map/culling systems, swappable forward and deferred renderers and picking buckets on WebGPU, calls the 2D-texture and render-to-texture pipeline a continual source of pitfalls, and criticises WebGPU for leaving limitations and quirks to application developers. — [Use.GPU Goes Trad](https://acko.net/blog/use-gpu-goes-trad/)
- Indicators of general-renderer effort from the engines themselves: three.js's WebGPU renderer is still labelled experimental in r186; Babylon.js had to hand-write WGSL versions of its core shaders (8.0) to drop a 3 MB+ converter; Figma reports Emscripten's WebGPU bindings are deprecated in favour of Dawn's emdawnwebgpu. — [three.js WebGPURenderer manual](https://threejs.org/manual/pages/webgpurenderer.html); [Babylon.js 8.0 announcement](https://blogs.windows.com/windowsdeveloper/2025/03/27/announcing-babylon-js-8-0/); [Figma: rendering powered by WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)
- Thin layers (TypeScript): TypeGPU 0.12.7 (MIT, pre-1.0, about 286,000 weekly downloads) describes itself as a thin layer between JavaScript and WebGPU/WGSL; luma.gl 9.4.2 (`@luma.gl/core`, about 1.05M weekly downloads) provides a device API from the vis.gl project; regl 2.1.1, twgl.js 7.0.0 and OGL 1.0.11 are WebGL-era helpers (OGL's repository was last pushed in April 2025). — [typegpu on npm](https://www.npmjs.com/package/typegpu); [visgl/luma.gl](https://github.com/visgl/luma.gl); [regl](https://github.com/regl-project/regl); [twgl.js](https://github.com/greggman/twgl.js); [oframe/ogl](https://github.com/oframe/ogl)
- Rust/C++ routes: wgpu (about 18,300 stars; the implementation Firefox uses for WebGPU) and Bevy (about 49,000 stars, Apache-2.0) are active; Dawn is Chromium's implementation and is what Figma uses natively. — [gfx-rs/wgpu](https://github.com/gfx-rs/wgpu); [gpuweb implementation status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status); [bevyengine/bevy](https://github.com/bevyengine/bevy)
- Smaller WebGPU-native engines exist: Orillusion (MIT, about 5,200 stars, describes itself as a pure WebGPU engine, pushed October 2026) and Galacean (MIT, about 5,900 stars). — [Orillusion](https://github.com/Orillusion/orillusion); [galacean/engine](https://github.com/galacean/engine)
- Engine-extension middle path, as documented by each engine: three.js `LightingModel` subclasses and TSL node slots; Babylon.js material plugins and Node Material; PlayCanvas chunk overrides and `ShaderMaterial`. — [LightingModel.js (r186)](https://github.com/mrdoob/three.js/blob/r186/src/nodes/core/LightingModel.js); [Babylon.js material plugins docs](https://doc.babylonjs.com/features/featuresDeepDive/materials/using/materialPlugins); [PlayCanvas StandardMaterial API](https://api.playcanvas.com/engine/classes/StandardMaterial.html)

### Inferences
- Work list for a hand-rolled renderer to reach the baseline the engines already ship: glTF and KTX2/Basis loading; PBR with IBL prefiltering; shadows; a post chain (bloom, AO, temporal AA, tone mapping); GPU or BVH picking; instancing with partial buffer updates; a transparency strategy; gizmos and outlines; shader-variant and pipeline-cache management with asynchronous compilation; device-loss recovery; and either a WebGL 2 fallback (which doubles the shader-language surface unless a transpiler is built, as Figma did) or an explicit WebGPU-only stance (about 83% of surveyed sessions, see section 8).
- Benefits specific to this application: full control of the lighting loop and frame structure (for example a bespoke glint BRDF, a visibility-buffer or compute-culled sequin pass, exact transparency for sheer mesh), minimal bundle, and immunity from upstream breaking changes. Risks: long time before first production-quality pixel, exposure to browser/driver bugs that engines have already absorbed (Figma needed blocklists and a live fallback), key-person dependency, and a smaller hiring pool than for a mainstream engine such as three.js.
- The engine-extension path keeps loaders, shadows, IBL, post-processing and picking while concentrating custom effort on the BRDF and the instanced-crystal pipeline; its cost is coupling to engine internals that change (three.js per-release breaking changes; Babylon.js's unguaranteed injection points).
- Figma's and Onshape's reasons for hand-rolling (a 2D vector renderer with no existing equivalent; CAD-scale triangle streaming) are not the same problem as physically based fabric rendering, where the engines already provide most of the shading substrate.

### Gaps
- No quantified effort report (team size × duration) for building a PBR-grade WebGPU renderer for a shipped product was found; available accounts are qualitative.
- Engineering posts from Womp, Vectary, PlayCanvas or Babylon.js on the cost of their own renderer work were not retrieved.
- Rust-to-WebAssembly editor case studies (for example wgpu-based viewers running in browsers) were not researched.

## 7. Case studies: how and why were professional web creative tools built the way they were?

### Takeaway
In the verified cases, tools whose core value is a proprietary rendering or geometry engine built it themselves (Figma, Onshape), while 3D creative tools that need general scene rendering built on three.js (Plasticity on Electron with three.js; Spline v2's runtime on three.js's WebGPU renderer with a WebGL build alongside). The rendering stacks of Womp, Vectary, Sketchfab's viewer, Tinkercad, Adobe's web 3D tools and fashion-CAD web viewers could not be verified in this session.

### Cited Findings
- Figma: custom C++ renderer compiled to WebAssembly, WebGL since 2015 and WebGPU since 2025 with WebGL retained as fallback; reasons and lessons as in section 6. — [Figma 2015](https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/); [Figma 2025](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)

- Vectary's site describes browser-based, real-time rendering that it calls photorealistic and says works on any device, materials including refraction, absorption, subsurface scattering, clearcoat and thin-film, embeds, web AR and no-code 3D product configurators; it does not name its engine or graphics API. — [Vectary](https://www.vectary.com/)

### Inferences
- Lessons that transfer to a leotard design tool: keep a WebGL fallback and plan for device loss mid-session, not only at start-up (Figma); put heavy, deterministic computation where it is cheapest and send the client something it can draw fast (Onshape); a WebAssembly core pays off when the document model and memory layout dominate (Figma), which is less obviously the case for a scene of one garment plus instanced crystals; and a commercial 3D design tool can be shipped on three.js's WebGPU renderer if a WebGL build is maintained alongside (Spline).

## 8. Web-specific limits (texture sizes, memory, shader stalls, float textures, colour/HDR, pen latency) and reach across browsers, tablets and desktop packaging

### Takeaway
WebGPU is enabled by default in Chrome and Edge (Windows, macOS, ChromeOS since 113; Android 12+ since 121; Linux partially since 144/147), in Safari 26 on macOS, iOS, iPadOS and visionOS, and in Firefox on Windows (141) and macOS (145/147); it is not yet default in Firefox on Linux or Android, on some Android GPUs, or in Chrome on Windows-on-ARM. One survey reports a working WebGPU adapter in 83% of sessions. Texture dimensions are not the binding constraint (8192 is universal and 16384 nearly so); memory is, especially on iOS, and several niceties a painting tool wants — HDR canvas output, low-latency (desynchronised) canvases and raw pointer updates — are Chromium-only.

### Cited Findings

- `OffscreenCanvas`: Chrome 69, Firefox 105, Safari 16.4 (WebGL contexts from Safari 17); a WebGPU context on `OffscreenCanvas` is available in Chrome, Safari 26 and Firefox 141 (Windows only). — [MDN browser-compat-data: OffscreenCanvas](https://github.com/mdn/browser-compat-data/blob/main/api/OffscreenCanvas.json)
- Multithreaded WebAssembly needs `SharedArrayBuffer`, hence cross-origin isolation headers, which block ordinary third-party embeds; three-mesh-bvh's parallel BVH builder has the same requirement. — [Godot: exporting for web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); [three-mesh-bvh README](https://cdn.jsdelivr.net/npm/three-mesh-bvh@0.9.16/README.md)

### Inferences
- Memory arithmetic for the stated texture sizes: an uncompressed 8192 × 8192 RGBA8 texture is 256 MB (about 341 MB with mipmaps) and a 4096 × 4096 one is 64 MB (about 85 MB); block-compressed 8-bit-per-pixel formats cut that to a quarter, but textures the user paints into must stay uncompressed render targets. A few 8K paint layers therefore exceed what the reported iOS canvas budgets suggest is safe, so 8K painting is realistically a desktop-class feature with 4K (or tiled/virtual textures) on tablets.
- Because BC is available on about 87% of sessions and ASTC/ETC2 on about 47%, shipping fabric and HDRI assets as KTX2/Basis with run-time transcoding is the portable choice; all three JavaScript engines include the loaders.
- An iPad with Apple Pencil can only use WebGPU on iPadOS 26 or later; coalesced and predicted pointer events exist there (Safari 18.2+), but neither raw pointer updates nor desynchronised canvases do, so stroke latency on iPad Safari is bounded by the normal compositor path, whereas Chromium on Windows/ChromeOS offers lower-latency options.
- HDR canvas output should be treated as progressive enhancement for Chromium-based browsers (and Electron), not a baseline.
- Electron gives one known Chromium (currently 152, a few versions behind Chrome stable at 155–156) on every desktop OS, including WebGPU and HDR canvas; Tauri inherits each OS's webview, which means WebGPU on macOS only from macOS 26 and an unverified situation on Linux WebKitGTK.
- Dropping the WebGL 2 fallback would currently exclude roughly one session in six in the survey (most Linux users, Firefox on Android, older Android), fewer if the audience is mostly recent Windows, macOS and iPad devices.

### Gaps
- Authoritative, current per-tab memory ceilings for WebGPU/WebGL content on iOS/iPadOS Safari were not found; the canvas-memory figure is from 2022 and concerns 2D canvases.
- No measurements of 60–120 fps behaviour on integrated GPUs or Apple silicon for any engine were found; whether `requestAnimationFrame` runs at 120 Hz on ProMotion iPads in Safari was not researched.
- Which iPhone/iPad/Mac models Safari 26's WebGPU covers, and iOS-specific WebGPU limits, were not found; the survey's per-platform limit breakdown was not retrieved.
- Stylus latency measurements for Android/ChromeOS/iPad browsers and Apple Pencil hover support in Safari were not researched.
- WebGPU status in WebKitGTK (Tauri on Linux) is unverified.

## 9. Cost considerations: licences, hosting/CDN, and the backend implied

### Takeaway
Licences for the web-native options cost nothing and are permissive (MIT: three.js, PlayCanvas engine, R3F, drei, three-mesh-bvh, three-gpu-pathtracer; Apache-2.0: Babylon.js, Filament). Money goes into engineering time, optional per-seat tools (PlayCanvas Editor $15–50 per seat per month; Unity Pro $2,310 per seat per year above $200,000 revenue), and delivery — which is ordinary static hosting plus object storage for client-rendered options, but a GPU-backed server session per concurrent user for pixel streaming.

### Cited Findings
- Licences (verified in package/repository metadata): three.js MIT; Babylon.js Apache-2.0; PlayCanvas engine MIT; Filament Apache-2.0; react-three-fiber MIT; drei MIT; three-mesh-bvh MIT; three-gpu-pathtracer MIT; pmndrs postprocessing Zlib; TypeGPU MIT; Godot MIT. — [three](https://registry.npmjs.org/three/latest); [@babylonjs/core](https://registry.npmjs.org/@babylonjs/core/latest); [playcanvas](https://registry.npmjs.org/playcanvas/latest); [google/filament](https://github.com/google/filament); [@react-three/fiber](https://registry.npmjs.org/@react-three/fiber/latest); [three-mesh-bvh](https://registry.npmjs.org/three-mesh-bvh/latest); [postprocessing](https://registry.npmjs.org/postprocessing/latest); [typegpu](https://registry.npmjs.org/typegpu/latest); [godotengine/godot](https://github.com/godotengine/godot)
- PlayCanvas Editor (optional; the engine is usable without it): Free $0 with 1 GB, Personal $15/month with 10 GB, Organization $50 per seat/month with 50 GB. — [PlayCanvas plans](https://playcanvas.com/plans)

- Pixel Streaming requires running the packaged application on a PC or cloud server plus a signalling server, matchmaker and SFU. — [Unreal Engine Pixel Streaming docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/pixel-streaming-in-unreal-engine)
- Onshape's architecture — geometry servers doing regeneration, solving and tessellation for browser clients — is an example of a server fleet implied by a server-computed design tool. — [Onshape](https://www.onshape.com/en/blog/how-does-onshape-really-work)

### Inferences
- For any client-rendered option (three.js, Babylon.js, PlayCanvas, Filament-WASM, a hand-rolled renderer, Unity/Godot web builds) the application itself is static files; marginal delivery cost per user is close to zero on a zero-egress object store, and the engine choice does not change it materially — bundle size affects load time more than money.
- The backend implied by the product, independent of engine: authentication and accounts; a design document store (parametric design data plus user-painted texture layers, which at 4K–8K are tens to hundreds of megabytes each uncompressed and therefore need compression or tiling before upload); an asset library on a CDN (HDRIs, fabric and crystal materials as KTX2); and optionally server-side workers for high-resolution or path-traced exports and tech-pack generation.
- The cost asymmetry between options is therefore almost entirely engineering time: pre-built engines trade licence-free capability for upgrade and integration work; a hand-rolled renderer front-loads months of infrastructure; a game-engine export adds seat licences (Unity) or per-session GPU spend (Unreal Pixel Streaming).

### Gaps
- Unreal Engine licence terms could not be retrieved (HTTP 403), and no cloud GPU price was retrieved for sizing Pixel Streaming.
- No total-cost-of-ownership comparison (engineering time by option) from a neutral source was found.
- CDN and storage pricing was sampled from one provider only.
